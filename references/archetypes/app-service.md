# 类型：app-service（可运行的应用 / 服务 / Web / 桌面）

## 识别
有运行入口（server/app/main）、Web 框架或桌面框架依赖、Docker/Compose、前后端目录。`classify_repo.py` 主类型为 `app-service`。

## 什么算好
- 能按 README 一把跑起来；配置有 `.env.example` 与默认值说明
- 业务边界清晰，依赖方向单向，**边界有工具/测试守护**（而不只是文档）
- 失败有兜底（超时/重试/降级），状态存放位置明确，重启不丢关键数据
- 有迁移机制（有状态应用）、日志/可观测、健康检查
- 测试覆盖业务规则的边界而非只有 happy path；CI 至少跑测试

## 必读文件
1. 入口与装配（应用工厂/main）  2. README 最吹的功能对应的核心业务文件  3. 一个测试文件
4. 架构/设计文档 + 强制它的测试  5. Dockerfile / compose / CI workflow / `.env.example`

## 类型特有检查
- 追踪一条端到端主链路（见 `architecture-core.md`）：触发 → 业务判断 → 外部调用 → 落库/输出
- 默认鉴权是否开启、是否默认监听公网、CORS 配置与鉴权方式是否匹配（Cookie 才有 CSRF 面，Bearer 头一般没有）
- 外部依赖清单（`arch_probe` 的外部域名）：数据源/第三方服务是否可替换、是否有 fallback
- 升级与数据迁移路径；版本固定与 lockfile

## 类型特有红旗
- 无登录即暴露管理接口；默认弱口令/固定密钥
- 单个类/文件跨数千行并承担多种职责（用 ast 测量，不要估算）
- 配置面持续膨胀（`.env.example`/config 文件在变更热点前列）
- 关闭 TLS 校验且无说明；吞异常；无超时的外部调用

## 维度解释
基础权重即可。H 看分层/边界/核心抽象；D 看测试 + CI 实际内容 + 迁移 + 可观测。

## 同类对手怎么选
同一问题域、同一用户、同一部署形态的 3–5 个应用；再加 1 个"上游/底座"（若依赖某框架）和 1 个"替代路线"（SaaS/CLI/库）。

## 报告章节
完整模板全部适用（架构图、核心链路、亮点/取舍、同类对比）。
