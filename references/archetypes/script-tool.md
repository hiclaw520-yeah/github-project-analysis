# 类型：script-tool（小型脚本 / 个人工具 / 单用途自动化；规模标记，常与其他类型叠加）

## 识别
`size_class` 为 tiny/small（<200 文件，常 <40 个代码文件），单人维护，根目录有 `main.py` 之类入口，依赖少。常与 app-service / cli-devtool 叠加。

## 评价原则：按"相对规模的合理期望"来评
- **不因缺少而扣分**：CI、架构文档、多包拆分、贡献指南、Docker
- **仍然要求**：**LICENSE**（没有就不能合法使用/改造）、密钥不入库、必要的风险声明（金融/账户/爬取类尤其）、README 能跑通
- 重点看：**核心逻辑是否正确且易于改造**（学习/借鉴场景的关键）、是否有最基本的测试、配置是否外置

## 什么算好
- 入口清晰、配置外置（`.env.example`）、依赖锁定
- 核心逻辑小而清楚，关键假设有注释
- 有针对核心逻辑的测试（哪怕很少）
- 对已知局限诚实（README 写明"不含回测/不含风控"之类）

## 必读文件
入口脚本；核心逻辑文件（通常 1–3 个）；配置；测试；README 的运行说明。

## 类型特有检查
- 核心逻辑的**领域正确性**：按领域补充清单抽查（如金融类的交易规则/复权/前视偏差见 `domains/quant-trading.md`）
- 活跃度：多久没提交；是否已被 fork 出更活跃的分支
- 是否有 LICENSE；依赖是否有已弃坑项
- 运行安全：是否会把密钥/数据发往第三方（通知渠道、LLM）

## 类型特有红旗
- 无 LICENSE（一票否决，若用户要使用）
- 硬编码的规则（魔法数字）在不同场景下会误判，且无说明
- 数据源是脆弱的爬取接口且无兜底，README 却宣称稳定

## 维度解释
B −3、D −3；F 与 LICENSE **不降标**；H 看"可改造性"；A 看年龄归一化后的涨星（老项目日均涨星天然低）。

## 同类对手怎么选
同任务的其他个人/小型项目与一个成熟平台级项目（用于定位"小而美 vs 大而全"）。
