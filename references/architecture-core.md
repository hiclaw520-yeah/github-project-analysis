# 架构 · 核心 · 亮点 分析方法

目标：回答四个问题——**它是怎么搭起来的？哪条链路是核心？真正的亮点是什么？为此付出了什么代价？**

本文以"有运行时的代码项目"为默认。其他类型的对应做法见文末"不同类型怎么做"。

先跑 `python scripts/arch_probe.py <克隆目录>` 得到线索（目录规模、入口、技术栈、模块依赖图、外部域名、变更热点），再按下面五步把线索变成结论。**脚本输出是线索，不是结论。**

## 目录
1. 画系统全景（C4-lite）
2. 追踪一条端到端主链路
3. 找核心抽象与"护城河"
4. 提炼亮点（必须有证据）
5. 记录取舍与缺陷
6. 架构图怎么画
7. 常见陷阱

---

## 1. 画系统全景（C4-lite，三层就够）

| 层 | 回答 | 线索来源 |
|---|---|---|
| **上下文** | 谁用它？它依赖哪些外部系统（数据源、LLM、通知、券商）？ | README、`arch_probe` 的外部域名、`.env.example` |
| **容器/进程** | 跑几个进程？存储是什么？前后端怎么分？部署形态（单容器/compose/Actions/桌面端）？ | Dockerfile、compose、入口文件、依赖里的 DB/队列 |
| **组件/模块** | 业务按什么边界切？依赖方向是什么？谁是枢纽、谁是编排层？ | 模块依赖图的被依赖 Top（枢纽）、依赖他人 Top（编排层） |

读依赖图时的判断规则：
- **被依赖最多的**是基础设施层（持久化、数据、调度）。如果枢纽是某个业务模块，说明业务被当作公共库用，边界在泄漏。
- **依赖他人最多的**是编排层（通常合理）。如果它还很大、改动频繁，就是"上帝模块"。
- **双向依赖（环）**说明两个模块实际上是同一个领域被拆成了两半，或抽象层次放错。`arch_probe` 把环分成两类：
  **硬环**（模块顶层互相导入，导入顺序出问题会真的炸）与**靠延迟导入 / `TYPE_CHECKING` / `import type` 掩盖的环**（运行时被绕开，但设计上仍然双向耦合）。后者在类型互引很多的库里很常见，未必是缺陷，但要如实区分；前者要重点看。
- 区分"文档声称的边界"和"测试/工具强制的边界"，并**精确描述强制的范围**（例如测试只卡了 A→B 的方向，但没有检查环）。

## 2. 追踪一条端到端主链路

选**README 最吹的那个功能**，从触发点一路读到落库/输出，每一跳记录"文件:函数 → 它做了什么 → 经过了什么抽象"。典型链路形态：

- 服务类：`HTTP 路由 → service → repository → DB`
- 定时/监控类：`调度器 → Agent/Job → 数据采集 → 业务判断（含闸门，如交易日历）→ AI/规则 → 通知（含去重/节流）→ 运行记录`
- 数据管道类：`采集 → 清洗 → 存储 → 计算 → 输出`

在每一跳问三个问题：
1. **失败时怎么办？**（超时、重试、降级、failover、幂等）
2. **状态存在哪？**（内存/DB/文件；重启后会怎样）
3. **谁拥有这个决定？**（规则在哪一层；是否被散落在多处）

读不完整条链也要写明"读到哪一跳为止"。

## 3. 找核心抽象与"护城河"

**核心抽象**＝去掉它整个系统就散架的 3–5 个类/接口/表。找法：
- 依赖图里被依赖最多的模块里，最常被其他模块 import 的类
- 基类/ABC/Protocol（插件点往往在这里）
- 贯穿主链路每一跳的数据结构（如 `Signal`、`AgentRun`、`Quote`）
- 数据库里被引用最多的表

**护城河**要诚实评估，分四类，并标注属于哪类：
| 类型 | 例子 | 可复制性 |
|---|---|---|
| 算法/模型独创 | 自研信号、专有模型 | 低（若真有） |
| 数据/渠道独占 | 独家数据源、已集成的 N 个渠道 | 中 |
| 工程集成广度 | 多市场、多通知、多模型兼容、PWA、新手引导 | 高（时间可换） |
| 社区/品牌 | star 规模、生态 | 中 |

关键判断：**"powered by X" 的项目，核心算法在上游，自己的价值是集成与产品化**——要明说，不要把上游的能力算成它的亮点。

## 4. 提炼亮点（必须有证据）

一个合格的"亮点"需同时满足：
1. **具体**：能指到文件/函数/测试，不是"架构清晰""体验优秀"。
2. **有效**：能说出它解决了什么问题，没有它会怎样。
3. **可迁移**：别的项目也能借鉴（学习场景特别看这条）。
4. **非营销**：来自代码事实而非 README 措辞。

亮点分级：
- ⭐⭐⭐ 设计层：改变了系统结构的做法（如"用 AST 测试强制依赖方向"）
- ⭐⭐ 工程层：让系统更可靠/可维护的做法（如"AI 调用的错误分类 + 冷却 failover"）
- ⭐ 体验层：让用户更好用的做法（如"首次引导会校验用户真的完成了操作"）

每个亮点写成：`亮点名 — 证据(文件) — 解决什么 — 可迁移吗 — 代价`。

## 5. 记录取舍与缺陷

每个重要设计选择都有代价，把"好"和"代价"成对写，避免只夸不批：

| 选择 | 得到 | 付出 |
|---|---|---|
| 模块化单体 | 部署简单、边界清晰 | 模块间仍能通过 import 耦合，需靠测试守护 |
| 免费数据源爬取 | 零成本 | 接口随时变、限频、需关 TLS 校验等 |
| 依赖上游框架（如固定到某 tag） | 快速获得能力 | 上游升级/弃坑风险，调试要读上游 |

缺陷分三类标注：**结构性**（要大改才能修）、**局部性**（改一处即可）、**风险性**（暂时没出事但会出事）。每个缺陷挂证据，并区分"作者已知并在迁移"（如 README/测试里明确写了 legacy 在退役）与"未意识到"。

## 6. 架构图怎么画

交付时给一张**简图**，不要把脚本全量依赖图贴出去（40 条边没人看）：
- 用 Mermaid `flowchart LR` 或 `graph TD`，**节点不超过 12 个**，按层分组（subgraph）
- 画**依赖方向**，在边上标注关键事实（如"仅此处有环"）
- 主链路单独画一张时序/流程图，每一跳标文件名
- 图下面一句话说明"这张图想让你记住什么"

## 6b. 不同类型怎么做

| 类型 | "架构"换成什么 | "主链路"换成什么 |
|---|---|---|
| 内容 / 纯技能包 | **信息架构**：分组 → 条目 → 命令/工作流的层级图；条目模板是否统一；交叉引用关系 | 一次典型使用：用户措辞 → 触发哪条内容 → 产出什么 |
| 带代码的插件 / MCP 服务 | 运行架构 + **信任边界与权限面**（谁调用谁、能执行/读写什么、hooks 触发条件由谁控制） | 宿主 → 技能/工具 → 核心库 → 外部程序/数据 |
| 库 / 框架 | 模块与**公开 API 面** | 一次典型调用的路径 |
| CLI | 命令树 | 一个会写文件/调外部程序的命令的执行路径 |
| 研究 / 模型 | 数据 → 训练 → 评测 流水线 | 复现命令走到的每一步 |
| 模板 / 配置 | 目录结构 + 生成/部署流程 | 一次生成或部署 |

**monorepo / 大仓库**：不要通读。先看工作区包之间的依赖（`arch_probe` 对 JS/TS 工作区包做了解析），挑核心包和一个外围包读；报告里写明"抽样了哪些包"。

**语言覆盖**：`arch_probe` 的依赖图支持 Python、JS/TS（含工作区包）、Go；Rust/Java/C# 等暂不支持，此时在报告里写"依赖图未自动生成"，改为手动读入口与模块清单，不要编造图。

## 7. 常见陷阱

- **把目录结构当架构**。目录叫 `domain/` 不代表有领域模型；看 import 才是真依赖。
- **把文档当现实**。架构文档写的规则，要找到强制它的测试/工具，否则只是愿望。
- **热点文件的历史路径**。变更热点里可能包含已迁移/删除的路径，只看当前仍存在的文件；删除占比高说明发生过大重构，这本身是信息（"项目演进快 / 技术债在偿还"）。
- **用"行数÷函数数"估算长函数**。不准（实测推翻过）。用 `arch_probe` 第 7 节的 ast 精确测量：最长的函数、最长的类、>100 行函数占比。类 >1000 行基本是上帝类；单个函数过长常见于"注册表/配置加载/提示词拼装"，要看性质再定性。
- **配置膨胀信号**：变更热点里 `.env.example`、`config.py`、`config_registry` 排在前列，说明配置面在持续膨胀，上手与维护成本会上升。
- **把父子目录互引当循环依赖**（如根文件 `src` 与子目录 `src/x` 互相引用共享类型）。`arch_probe` 已排除，但手动判断时也要区分"同级模块真环"与"父子目录互引"。
- **忽视前端**。前端占比常不低（>30% 代码量），也要给一句评价（组件库、状态管理、国际化、测试）。
- **只夸亮点**。没有写出代价的亮点清单是营销稿。
