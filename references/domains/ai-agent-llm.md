# 领域补充：LLM / Agent / RAG / MCP / 多智能体项目

这类项目最容易出现"Demo 很惊艳、生产很脆弱"。通用九维之外，重点核对：

## 1. 是"编排"还是"套壳"

- 核心逻辑是自己实现的 agent loop/状态机，还是依赖 LangGraph / LangChain / CrewAI / AutoGen 等框架？依赖框架不是缺点，但要弄清**项目自身的增量价值在哪一层**（如：仅调用上游 → 价值在产品化与集成，不在多智能体算法）。
- 如果 README 写 "powered by X"：看依赖是**固定到 tag/commit** 还是浮动分支；上游升级会不会破坏它；是否做了适配层隔离。
- 有没有真正的**工具调用边界**（工具白名单、参数校验、权限分级），还是让模型任意执行？

## 2. 提示词与上下文管理

- 提示词放在哪：硬编码在代码里，还是独立目录/版本化管理（`prompts/` 目录是好信号）？
- 上下文如何构建：是否有 context builder、摘要/截断策略、token 预算？
- 是否把**真实数据**喂给模型，而不是让模型凭记忆回答。

## 3. 可靠性与成本

- **多模型/多提供商**：是否兼容 OpenAI 协议、支持本地模型（Ollama）、有 failover 与重试？
- **流式/超时/限流**的处理；错误是否分类（鉴权失败、额度不足、网络）。
- **成本计量**：是否记录 token 与耗时（`token-meter` 之类模块）；是否有预算/上限。
- **幂等与重入**：定时任务重复触发会不会重复调用、重复通知。

## 4. 评测与可观测

- 有没有 **eval**（离线评测集、回放、对历史输出打分）？没有 eval 的 agent 项目，质量无法客观比较。
- 运行记录：每次运行的输入、输出、耗时、成本是否落库？trace 是否可关联（trace_id、OpenTelemetry GenAI 语义）？
- 能否复现一次失败的运行。

## 5. 人在回路与安全

- 高风险动作（下单、发邮件、写文件、删数据）是否需要**审批**（approval 流程是好信号）？
- 提示注入防护：外部内容（网页、新闻、邮件）进入提示词前是否做隔离与标注？
- 数据外发：用户数据发给哪些 LLM 提供商？密钥存储是否加密、日志是否脱敏？
- MCP/工具服务器：来源是否可信、权限范围多大。

## 6. 学习价值的特别提示

AI 项目里最值得带走的常常不是"模型怎么调"，而是：
- 运行记录与成本表的数据建模
- 失败兜底与 failover 策略
- 把非确定性输出关进确定性流程（调度、审批、校验）的方式
- 评测与回放机制

读代码时优先找这些，而不是提示词本身。
