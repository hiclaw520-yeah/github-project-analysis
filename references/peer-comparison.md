# 同类产品对比方法

单看一个项目会高估或低估它。对比的目的是回答：**在这个赛道里它排第几？差异化是什么？什么场景该选它、什么场景该选别人？**

## 目录
1. 选对手（3–5 个，三种角色）
2. 采集：同一天、同一方法、原仓库
3. 对比矩阵（维度清单）
4. 归一化：让数字可比
5. 定位与结论
6. 陷阱清单（真实踩过的坑）

---

## 1. 选对手：3–5 个，覆盖三种角色

| 角色 | 含义 | 价值 |
|---|---|---|
| **上游/底座** | 它所依赖或模仿的项目 | 判断它的核心价值到底是不是自己的 |
| **直接竞品** | 同一用户、同一问题、同一形态 | 判断它的相对位置 |
| **替代路线** | 解决同一问题但路线不同（如：自托管 vs 云服务、框架 vs 成品、CLI vs Web） | 判断路线选择是否合理 |

找对手的办法（按可靠度排序）：
1. 仓库 README 里的 "Related / Alternatives / Inspired by / Powered by / Compared to"
2. 仓库的 **topics**，打开 `github.com/topics/<topic>` 按 star 排序
3. 依赖文件里点名的上游项目（如 `requirements` 里的 git 依赖）
4. 搜索 `"<项目类型> alternative"`、`awesome-<领域>` 列表
5. 中文圈再补：HelloGitHub、掘金/知乎/CSDN 的"开源项目盘点"（**只用来找名字，不要用来取数字**，见陷阱）

不要把明显不同量级或不同形态的项目放进矩阵凑数（如拿 20 个 star 的个人项目对比 6 万 star 的明星项目，除非目的就是定位差距）。

## 2. 采集：同一天、同一方法、原仓库

- **每个对手都从仓库页面取当前数据**（star、fork、issue/PR、最近提交、语言、协议、release、README），记录采集日期。
- 能克隆的跑 `local_probe.py`，至少取提交节奏与作者数（按邮箱）。
- **确认抓到的是原仓库**，不是 fork/镜像：看仓库页是否有 "forked from"，作者是否为项目官方账号，README 里引用的官方地址。搜索引擎常把大量镜像排在原仓库前面（有的显示 0 star）。
- 采集不到的字段写"未采集"，不要用旧文章里的数字补。

## 3. 对比矩阵（按需取舍，每列都要有来源）

**先按类型选矩阵行**——通用行（定位/规模与热度/维护/许可/商业）总是要有；类型行如下：

| 类型 | 类型行（替换下面"核心能力/架构/工程"里不适用的部分） |
|---|---|
| 内容 / 技能包 | 条目数量**与质量**（抽样）、规范合规率、description 触发质量、校验器与 CI、多平台适配、更新节奏、许可与署名 |
| 带代码的插件 / MCP | 技能/工具数、能力面（能执行/注入/联网？）、hooks 与安装方式、护栏（文字 vs 代码）、集成测试、多平台适配 |
| 库 / 框架 | API 面与稳定性、体积、依赖数、类型支持、兼容矩阵、版本纪律 |
| CLI | 安装成本、首次价值时间、可脚本化、权限与副作用、更新机制 |
| 研究 / 模型 | 复现难度、结果对齐、硬件成本、数据与权重可得性 |
| 应用 / 服务 | 下表全部适用 |

通用与应用型行如下：

| 类别 | 维度 | 说明 |
|---|---|---|
| 定位 | 一句话定位 / 目标用户 / 主场景 | 学术研究、个人使用、团队、生产？ |
| 形态 | 是库/框架/成品应用/服务？部署方式 | CLI、Web、桌面、Actions、Docker、SaaS |
| 范围 | 市场/数据/语言/平台覆盖 | 例如覆盖哪些市场、模型提供商 |
| 核心能力 | 3–5 个关键能力的有无（✓/部分/✗） | 以**用户任务**为列，而不是以技术名词为列 |
| 架构 | 技术栈、模块化程度、扩展点（插件/自定义策略） | 来自 `arch_probe` |
| 规模与热度 | star、fork、近 90 天提交、贡献者(按邮箱)、release 节奏 | 见"归一化" |
| **代码层指标** | 测试行/源码行、>1000 行文件数、最长类、>100 行函数占比、依赖环对数、CI 内容（语法/lint/类型/测试分片/前端） | 来自 `local_probe` + `arch_probe`，**对手也要克隆跑**；同口径、可比性强 |
| 工程 | 测试比例、CI 内容、迁移、可观测 | 来自 `local_probe` |
| 文档与上手 | 首次跑通耗时、文档语种、是否有引导 | 能实测就实测 |
| 风险与合规 | 许可证、免责声明、数据外发、对第三方的依赖 | |
| 商业与可持续 | 赞助、联盟链接/邀请码、公司背书、付费版 | 见 `extra-checks.md` |
| 成本 | 使用成本（LLM 调用、数据源 token、服务器） | 对个人用户常常是决定性因素 |

## 4. 归一化：让数字可比

- **按年龄归一**：日均涨星 = star ÷ 创建天数；月均提交；不要拿 3 年项目与 6 个月项目比绝对值。
- **看增长形态**而非总量：是否上过 Trending、是否出现一次性突刺。
- **Fork/Star 比要结合部署方式解读**：如果推荐部署方式就是"Fork 后跑 GitHub Actions"，fork 数会接近 star 数（比值可达 0.8 以上），这反映"部署方式"而不是"二次开发活跃"。此时改看：独立提交者数、issue 质量、PR 合并数。
- **团队规模**：用按邮箱去重的作者数与头号作者占比，不用 star 推断。
- **语言/地域偏差**：中文圈项目在中文社区传播强，国际 star 可能偏少，反之亦然；说明受众而非判优劣。

## 5. 定位与结论（交付物）

必须产出：
1. **对比矩阵**（≤ 8 列 × ≤ 12 行，其余放附录）
2. **定位一句话**：它在赛道里的位置，如"功能最全的自托管盯盘+纸盘平台，但社区规模远小于头部"
3. **差异化清单**：它独有的 2–3 点 vs 它明显落后的 2–3 点（挂证据）
4. **场景 → 选谁**：
   - 想要 X → 选 A，因为…
   - 想要 Y → 选 B，因为…
   - 想学习 Z 的实现 → 读 C，因为…
5. **迁移/组合建议**：能否组合使用（如上游框架 + 此项目的工程层）；换到竞品的迁移成本是什么（数据、配置、习惯）

## 6. 陷阱清单（真实踩过的坑）

- **第三方文章数字过时/互相矛盾**：同一个仓库在不同文章里可能被写成 5.5k、29k、63k star（不同时间点）。一律回到仓库页面取数，并写明日期。
- **镜像与 fork 干扰搜索**：搜项目名常返回大量 fork/镜像；确认原仓库再取数。
- **Fork 即部署**造成 fork/star 比虚高（见上）。
- **Star 排名当质量排名**：热度高的项目往往因分发优势（零成本部署、视频教程、榜单）而非技术更好。把"分发能力"与"技术质量"分开写。
- **拿对手的营销话术当事实**：对手的 README 同样需要"声明核对"。
- **只比功能清单**：功能多不等于好；看每个功能的实现深度（有无测试、有无规则建模）。
- **比较维度偏向被评估项目**：选维度前先想"如果我先分析的是对手，我会选哪些维度"，避免量身定做。
- **缓存页数据新鲜度**：页面上的 "Updated" 日期早于克隆里最近提交，说明抓到的是缓存页，star 数是下限，必须标注。
- **同一仓库在不同日期差几倍**：实测某仓库快照从 4.8k → 23.5k → 46.7k → 62.8k；二手来源（star-history、oosmetrics、各类榜单）只能作"带日期的参考"，并写明是二手。
- **仓库页取不到时的替代**：官方组织/用户主页（列出各仓库 star/fork/issue/PR/协议）是可靠的一手来源。
- **主页数字会掩盖结构差异**：热度最高的对手可能藏着巨大的上帝类、而热度低的反而结构更好。务必加代码层指标。
- **对手红旗同样要复核**：对手仓库里的 `sk-…` 命中常是测试夹具占位符，别当成泄露。
- **忽略成本**：自托管项目的 LLM/数据源/服务器成本，常常比功能差异更影响最终选择。
