# 评分细则（rubric）：类型无关的九维 + 类型适配

这套维度适用于任何 GitHub 项目（应用、库、CLI、Agent 技能包/插件/MCP、内容集合、研究代码、模板、小脚本……）。
**维度不变，但每个维度用什么信号来判断，随项目类型而变。** 不要拿"测试覆盖率 / 架构图 / Docker"去衡量一个纯文档仓库，也不要拿"有没有 CI"去苛责一个 30 个文件的个人脚本。

## 目录
1. 用法（四步）
2. 规模校准
3. 权重（按目的）与类型调整
4. 九维定义与分类型信号
5. 锚点（0–5 分）
6. 总评、结论映射、一票否决
7. 修正项

---

## 1. 用法（四步）

1. 用 `classify_repo.py` + 读 README 确认**类型**（可混合）与**规模档位**。
2. 读对应的 `references/archetypes/<类型>.md`，里面写明了该类型"什么算好、必读什么、特有红旗、哪些维度要重新解释"。
3. 按下面第 3 节取权重，按类型调整后**归一化到 100**；某维度对该项目确实不适用就记 `N/A` 并从总分里剔除（不要给 0 分，也不要凭空给中间分）。
4. 逐维打分，每个分数写一句**证据**（文件路径/数字/采集日期）。

混合型（如"带 TypeScript 代码的插件"）：按**各自适用的部分**分别取信号，在报告里写明"代码部分 / 内容部分"各看什么。

## 2. 规模校准（先校准期望，再打分）

规模用 `classify_repo.py` 的 `size_class`：tiny(<40 文件) / small(<200) / medium(<1000) / large(<3000) / huge(≥3000)。

| 规模 | 合理期望 | 不应因缺少而扣分 | 仍然要求 |
|---|---|---|---|
| tiny / small，个人项目 | 能跑通、有 README、核心逻辑有基本测试 | CI、架构文档、多包拆分、贡献指南 | **LICENSE**、密钥不泄露、必要的风险声明 |
| medium | 有测试与 CI、基本模块边界、依赖管理 | 完整的 ADR/运维文档 | 同上 + 变更可追溯 |
| large / huge | 分层与边界被工具守护、CI 分层（lint/类型/测试/集成）、发布流程、安全策略 | — | 同上 + 依赖与供应链治理 |

"相对规模的合理期望"是评分的基线：一个 1.3k 行的个人脚本没有 CI 是正常的，一个 34 万行的 monorepo 没有 CI 才是问题。

## 3. 权重（按目的）与类型调整

基础权重（合计 100）：

| 维度 | 学习 | 直接使用 | 选型对比 | 研究为什么火 |
|---|---|---|---|---|
| A 热度真实性 | 3 | 8 | 8 | 30 |
| B 维护与可持续 | 3 | 18 | 20 | 8 |
| C 质量（代码 / 内容） | 15 | 10 | 6 | 3 |
| D 验证与可靠性 | 10 | 20 | 15 | 3 |
| E 文档与上手 | 10 | 8 | 15 | 12 |
| F 安全、合规与风险 | 3 | 18 | 8 | 3 |
| G 学习价值 | 25 | 0 | 2 | 20 |
| H 结构与核心设计 | 21 | 8 | 8 | 6 |
| I 竞争力与差异化 | 10 | 10 | 18 | 15 |

类型调整（在基础权重上加减后再归一化；幅度是建议值，写进报告说明即可）：

| 类型 | 调整 |
|---|---|
| app-service | 无需调整 |
| library-framework | D +3（兼容性/版本纪律/API 稳定）、E +2（API 文档）、B +2 |
| cli-devtool | F +3（安装方式、权限、遥测）、E +2（上手速度） |
| agent-skill-plugin | **F +6**（hooks/脚本/权限/安装器/提示注入面）、C 以"内容与指令质量"解释、D 以"校验与一致性"解释 |
| content-collection | D 以"准确性/链接/校验"解释、B 看"更新频率与勘误"、H 看信息架构 |
| research-model | D 以"可复现（环境、种子、数据、评测）"解释、F +2（数据与模型许可） |
| template-config | E +3（能否一键用）、F +3（默认值是否安全）、D 看"生成物能否直接跑通" |
| script-tool | B −3、D −3（不苛求 CI），**F 与 LICENSE 不降标**；H 看"是否易于改造" |

## 4. 九维定义与分类型信号

每个维度先问通用问题，再看该类型的具体信号。

### A 热度真实性 —— star 是自然增长还是运营/刷出来的？有人真在用吗？
- 通用信号：Fork/Star 比（常见 0.1–0.3；**先看部署方式**——"Fork 后跑 Actions"会让比值逼近 1）；日均涨星与是否上过 Trending；watchers/star 比；开放 issue/PR 体量；下载量/依赖方（npm/PyPI/Docker）；贡献者数量与分布。
- 内容/技能包：看 issue 里是否有真实使用反馈而非灌水；外部引用/二次开发（fork 里有无衍生）。
- **异常增长要标注并核验**：>500 星/天的持续增长、star 与 issue/PR/watchers 严重不成比例、提交历史与页面计数对不上。深度核验需 API：抽样 stargazers 的账号年龄/粉丝/仓库数（`gh api repos/<o>/<r>/stargazers`），或对比 star-history 曲线。**没做就写"未核验"，不要下"刷星"结论。**
- 页面计数不可单独信任：必须与克隆交叉验证（实测过页面"提交总数 3"而克隆有 3392 次）。

### B 维护与可持续 —— 还在更新吗？只靠一个人吗？出了问题有人管吗？
- 通用信号：近 30/90 天提交与"近 30 天占全史比例"（>50% 表示爆发式/刚开源）；按月曲线；**按邮箱去重**的作者数与头号占比（>85% 单人）；活跃贡献者（≥3 次提交）数；release/tag 纪律；issue/PR 积压与响应；是否归档；商业动机（赞助、联盟链接、自营站点导流——利好持续投入，但要标注）。
- 内容/技能包：内容更新节奏、是否跟随上游规范（如技能/插件规范）变化、勘误响应。
- 提交高度集中在几天内：可能是刚开源、历史迁移、批量/自动化提交——要据此修正节奏判断，并说明原因未知。

### C 质量（代码 / 内容）
- 代码类：文件与函数体量（用 `arch_probe` 的 ast 精确测量，不要估算）；命名、注释、类型/校验；重复与过度抽象；"上帝类/上帝文件"。
- 内容类（文档、技能、提示词、教程）：**具体性**（指令是否可执行、有无输入/输出格式、边界与反例）、**准确性**（抽查事实/引用/数字）、**一致性**（术语、结构模板、同类条目是否同样完整）、**去重**（是否大量近似条目）、**署名与来源**（引用框架/书籍是否标注）。
- 研究代码：与论文描述是否一致、关键超参/设置是否可见、是否有明显"为跑分而写"的捷径。

### D 验证与可靠性 —— 怎么知道它是对的？能不能放心改？
- 应用/库/CLI：测试行/源码行（<0.1 弱，0.2–0.6 良好，>1 很重）；抽读一个测试看断言的是行为还是仅 mock；CI **实际内容**（只构建=弱；测试=及格；lint+类型+测试分片+前端+集成/真实环境=强）；依赖锁定；迁移；错误处理与兜底；可观测性。
- 内容/技能包：自带校验器（并看它校验什么、CI 是否调用）、交叉引用检查、链接有效性、清单与磁盘一致、示例是否可运行、是否有评测集（eval）。
- 研究/模型：环境可复现（锁定依赖、种子、数据来源与版本）、评测脚本、是否给出可对照的结果。
- 模板/配置：生成物能否直接跑通、有无自检。
- **原则：不要执行未审阅的仓库脚本去"验证"。**读校验器源码判断其能力即可。

### E 文档与上手 —— README 跑得通吗？设计取舍有人写下来吗？
- 通用信号：Quick start 是否完整可跑、版本/环境要求、首次启动的坑、配置说明、架构/设计文档、贡献指南、多语言文档（是否同步）。
- 技能包/插件：安装方式（是否多平台）、每个技能的使用示例、触发词说明。
- **README 与现实一致性**见"声明核对"（挑 3 条最强承诺去验证，含数量类声明："69 个技能/42 个工作流"这类可以精确核对）。

### F 安全、合规与风险
- 通用：许可证（**无 LICENSE = 默认保留所有权利，不能合法使用/二次开发**）、密钥泄露、危险调用、数据去向与隐私外发、免责声明、依赖与供应链（版本固定、git 依赖、版本漂移）。
- **agent-skill-plugin 特别项**：hooks（会自动执行命令；看触发条件由谁控制、是否向模型注入"无需确认直接执行"的指令）、安装脚本（`curl | sh`：先读后评）、技能自带脚本（联网/子进程）、过宽的工具权限（`Bash(*)`）、MCP 服务能力面（能执行/注入/读写什么）、提示注入措辞。
- **双重用途领域**（逆向、渗透、爬虫、绕过类）：看有无明确的合法使用声明与禁止项、责任披露流程、代码层护栏（授权/范围/只读/沙箱）、社区治理；"护栏主要是文字声明"与"代码里有强制机制"要区分，没发现≠不存在，如实写"抽样未发现"。
- 金融/医疗/法律类：风险声明缺失是红旗。

### G 学习价值 —— 值不值得花时间读？
- 有无**可迁移的设计**（能指到文件）；复杂度对学习者是否友好（体量大时能否给出"只读哪几个文件"的路径）；设计取舍是否有文字说明；领域知识密度；**反面教材价值**（要明说是反面教材）。
- 内容类：框架/方法论的组织方式是否值得借鉴；模板结构是否可复用。

### H 结构与核心设计
- 代码类：分层与依赖方向、边界是否被工具强制、**同级模块间的环**（父子目录互引不算；**硬环**＝模块顶层互相导入，比"靠函数内延迟导入/TYPE_CHECKING 掩盖的环"更严重，两者分开写）、核心抽象、主链路每一跳的失败处理与状态归属（方法见 `architecture-core.md`）。
- 内容类：**信息架构**——分类是否清晰、粒度是否一致、条目间分工与交叉引用、有无统一模板、新增一条内容的成本。
- 插件/MCP：能力边界与职责划分、工具/技能的分组、与宿主的集成点、可扩展点。

### I 竞争力与差异化
- 在 3–5 个同类里排第几？差异化是代码事实还是 README 措辞？护城河类型（算法/数据/集成广度/社区/内容独占）与可复制性？
- 热度与质量分开写：分发强的项目结构未必好（实测过 6 万星项目有 5000 行的"上帝类"）。
- 无可比对手时写"未做同类对比"并给出建议对手清单，而不是硬凑。

## 5. 锚点（0–5 分，可给 0.5）

- **5**：显著优于同规模同类型项目，有可核验的强证据
- **4**：明显好于平均，只有少量可接受的缺口
- **3**：合格，有明确可修补的短板
- **2**：存在影响使用/学习的实质问题
- **1**：严重问题或基本缺失
- **N/A**：该维度对此项目不适用（写明原因），**不是 0 分**

打分前先问："对同规模、同类型的项目来说，这样算几分？"

## 6. 总评、结论映射、一票否决

加权总评 = Σ(分数 × 归一化权重) / 100（N/A 剔除后重新归一化）。

- ≥ 3.8 且无单项 ≤ 1 → 🟢 值得精读 / 可放心使用
- 2.8–3.8，或有单项 ≤ 1 → 🟡 选择性学习/使用（**点名只学/只用哪部分**）
- < 2.8 → 🔴 不建议投入
- 学习与使用**分别给结论**，二者可以不同（如"很值得学、不建议直接上生产"）。

**一票否决（直接标 🔴 并写明原因，除非用户明确接受该风险）：**
- 用户要使用/商用，但项目**无许可证**
- 发现密钥/凭据泄露，或恶意代码迹象
- 要在用户机器上执行的 hooks/安装脚本无法审阅（混淆、远程拉取后执行且不可固定版本）
- 明显滥用导向的双重用途项目，既无合法使用边界又无任何护栏，而用户要部署

## 7. 修正项

- **新项目（<3 个月）**：B 看当前节奏而非历史；A 参考作者过往项目。
- **爆发式提交（近 30 天占全史 >50%）**：先找原因（刚开源/迁移/批量提交/AI 驱动开发），写明"无法确定"也行，但不能当作稳定维护节奏。
- **单人项目**：B 不扣到底，但"直接使用"时写明"需自备 fork/接手能力"。
- **AI 辅助开发（提交带 AI 署名、有 AGENTS/CLAUDE 配置）**：**不因此扣分**；转而检查测试是否守住行为、边界是否被工具强制、重复代码是否整理。"高比例 AI 提交 + 无测试 + 无校验"才是风险组合。
- **大厂/基金会项目**：A、B 通常高分，更要核对 C、D 是否因体量变慢变重，以及是否真适合小规模场景。
- **数字阈值只是示例锚点**：同一指标要结合类型、规模、项目年龄解读。
